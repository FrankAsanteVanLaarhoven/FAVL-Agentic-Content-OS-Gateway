# M1.5 — Credential and Installation Lifecycle

**Status:** planned, not started. **Raised:** 2026-08-05, at the M1.4 boundary.
**Predecessor:** M1.4 (connector lifecycle) — complete, gated at 42/42.

This document exists so M1.5 can begin in a clean context. Everything below
was decided at the end of M1.4; re-deriving it would waste a session and risks
arriving somewhere different.

## Core invariant (I13, to be added to ADR 0001 when implemented)

> An invocation may use only the credential version authorised for that
> connector and tenant at execution time; raw secret values must never become
> connector state, events, traces, logs, or API output.

Two halves, and they fail differently. The first is an authorisation bug —
using a credential that was withdrawn. The second is a disclosure bug — a
secret leaving the boundary. Both need their own gate; a test for one will not
notice the other.

## Scope

```
connector package provenance
manifest validation
credential reference creation
credential rotation
credential revocation
version binding between connector and credential
audit and outbox events
no raw secret persistence
invocation-time retrieval
stale credential rejection
rollback-safe rotation
```

Suggested order — credentials first, because the core invariant is about
them and provenance can be added around a working credential model:

- **M1.5a** credential versioning, rotation, revocation, stale rejection,
  invocation-time retrieval, no raw persistence, audit + outbox
- **M1.5b** package provenance, manifest validation, required-key binding to
  the `INSTALLED` lifecycle state

## What already exists — build on it, do not rebuild it

- `app/security/secrets.py` — references are `secret://connector/<name>/<key>`
  and `secret://tenant/<id>/<key>`, resolved through `SecretResolver`. **A
  connector cannot express a storage address at all**; the namespace derives
  from its own identity and tenant. Read that module's docstring before
  touching it — it records an `env:` design that was removed for cause.
- `ConnectorRecord.credentials_rotated_at` — added in migration 0008, written
  by the `connector.credentials_rotated` transition. Currently a timestamp
  with nothing behind it. M1.5 gives it a referent; do not add a second one.
- `POST /v1/connectors/{id}/rotate-credentials` — exists, records an audit
  entry and changes no state. It is the endpoint M1.5a fills in.
- `connector_audit` — append-only, trigger-enforced. Credential events belong
  in it, not in a parallel table.
- `redact_config` and `tests/test_adapters.py` redaction tests — the existing
  defence for the disclosure half of I13.

## Design decisions already made

### One active version per (connector, key), enforced by the database

```sql
CREATE UNIQUE INDEX uq_credential_active
  ON connector_credentials (connector_id, key)
  WHERE status = 'active';
```

A partial unique index, not application logic. "Exactly one authorised
version" is the invariant; two active rows is the failure, and the database
is the only thing that can refuse it under concurrency.

**Read ADR 0001 I7a first** — a partial index whose predicate referenced a
literal rather than its column has already been a defect here once.

### Status set, and why superseded is retained

```
pending | active | superseded | revoked
```

`superseded` is kept rather than deleted, because rollback-safe rotation means
returning to the previous version, and a deleted row cannot be returned to.
`revoked` is terminal and one-way, mirroring connector revocation for the same
reason: restoring a revoked credential would return a compromised secret to
service without rotating it.

### Version pinned at execution time, recorded on the invocation

The invariant says *at execution time*, and that is what to implement:
resolution reads the active version when the adapter runs, and the version
actually used is written to the invocation record.

**This is a deliberate divergence from the connector-authority snapshot**,
which ADR 0002 pins at *acceptance*. Today the two coincide, because execution
is synchronous and follows acceptance within the same request. Under
asynchronous execution they can diverge, and the decision of which wins
belongs at the dequeue checkpoint — see REV-001 in `docs/DEBT.md`. Record the
reconciliation there rather than silently choosing.

### No raw secret persistence is a schema property, not a habit

`connector_credentials` stores a reference and metadata. There is no column a
raw value could go in. Enforce it three ways, because each catches a different
mistake:

1. no value column exists — a developer cannot store one without a migration
2. the create/rotate endpoints reject any payload field that is not a valid
   `secret://` reference, with the same forbidden-key check `ConnectorCreate`
   already applies
3. a test that asserts the emitted outbox event, the API response, and the log
   line for a rotation contain neither the reference's resolved value nor any
   high-entropy literal

### Events

```
connector.credential.created
connector.credential.activated
connector.credential.rotated
connector.credential.superseded
connector.credential.revoked
connector.credential.rollback
```

Payloads carry the reference, the version, the actor and the reason — never a
value. The existing outbox envelope (`event_id`, `aggregate_version`,
`schema_version`) applies unchanged.

## Gates — M1.5 is not done until each is observed

| # | Gate | Must be failure-validated by |
|---|---|---|
| 1 | An invocation uses only the active version | pinning a superseded version and watching the invocation be refused |
| 2 | Rotation is atomic | concurrent rotations; the partial index must refuse the second |
| 3 | Rollback restores the prior version | rotating twice, rolling back, asserting the invocation uses v1 |
| 4 | A revoked credential cannot be reactivated | attempting it and getting 409 |
| 5 | No raw secret reaches state, events, logs or API | planting a literal and asserting every surface refuses or redacts it |
| 6 | Credential revocation stops new use immediately | the I12 pattern: revoke mid-flight, next invocation refused |
| 7 | Manifest validation refuses a tampered package | altering a checksum |

Gate 6 is the one to write first. It is the same shape as M1.4's gate, which
is already proven, and it will expose the credential/connector authority
interaction early rather than at the end.

## Standing obligations that M1.5 must not trip

`make check` runs `scripts/check_dormant_obligations.py`. If M1.5 introduces
a retry path, a worker, or a credential-invalidation routine, REV-001/002/003
activate and the build fails until the named control exists. That is intended.
**Do not delete a trigger to make the build pass** — amend ADR 0002 with the
date and the reason, or add the control.

REV-002 is the likely one: credential rotation plus retry is exactly the
combination where an attempt inherits authority it should have had to re-earn.

## Explicitly out of scope

Emergency revocation. It stays designed-and-unbuilt (ADR 0002) until there is
a concrete operational requirement. Unreachable security code cannot be
failure-validated and therefore creates false confidence — the preconditions
for building it are listed in ADR 0002 and none are met.
