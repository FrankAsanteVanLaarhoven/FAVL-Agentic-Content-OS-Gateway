# M1.5 — Credential and Installation Lifecycle

**Status:** planned, not started. **Raised:** 2026-08-05, at the M1.4 boundary.
**Predecessor:** M1.4 (connector lifecycle) — complete, gated at 42/42.

This document exists so M1.5 can begin in a clean context. Everything below
was decided at the end of M1.4; re-deriving it would waste a session and risks
arriving somewhere different.

## Core invariants (I13a and I13b, to be added to ADR 0001 when implemented)

Two invariants, not one. They fail through different mechanisms and require
distinct tests; a test for either will not notice the other.

**I13a — credential authorisation**

> A withdrawn, superseded, revoked, or tenant-mismatched credential must not
> be used for a new authorised execution.

**I13b — credential confidentiality**

> A raw credential must not cross into persisted connector state, events,
> logs, traces, metrics, API responses, or audit payloads.

Note `metrics` and `audit payloads` in I13b. Both are easy to forget precisely
because they are the surfaces built for safety — a label value and an audit
record are the two places a developer feels entitled to put "just enough
context to debug this".

## Scope

```
connector package provenance
manifest validation
credential reference creation
credential rotation
credential revocation
version binding between connector and credential
audit and outbox events
no raw secret persistence
invocation-time retrieval
stale credential rejection
rollback-safe rotation
```

Suggested order — credentials first, because the core invariant is about
them and provenance can be added around a working credential model:

- **M1.5a** credential versioning, rotation, revocation, stale rejection,
  invocation-time retrieval, no raw persistence, audit + outbox
- **M1.5b** package provenance, manifest validation, required-key binding to
  the `INSTALLED` lifecycle state

## What already exists — build on it, do not rebuild it

- `app/security/secrets.py` — references are `secret://connector/<name>/<key>`
  and `secret://tenant/<id>/<key>`, resolved through `SecretResolver`. **A
  connector cannot express a storage address at all**; the namespace derives
  from its own identity and tenant. Read that module's docstring before
  touching it — it records an `env:` design that was removed for cause.
- `ConnectorRecord.credentials_rotated_at` — added in migration 0008, written
  by the `connector.credentials_rotated` transition. Currently a timestamp
  with nothing behind it. M1.5 gives it a referent; do not add a second one.
- `POST /v1/connectors/{id}/rotate-credentials` — exists, records an audit
  entry and changes no state. It is the endpoint M1.5a fills in.
- `connector_audit` — append-only, trigger-enforced. Credential events belong
  in it, not in a parallel table.
- `redact_config` and `tests/test_adapters.py` redaction tests — the existing
  defence for the disclosure half — I13b.

## Design decisions already made

### One active version per (connector, key), enforced by the database

```sql
CREATE UNIQUE INDEX uq_credential_active
  ON connector_credentials (connector_id, key)
  WHERE status = 'active';
```

A partial unique index, not application logic. "Exactly one authorised
version" is the invariant; two active rows is the failure, and the database
is the only thing that can refuse it under concurrency.

**Read ADR 0001 I7a first** — a partial index whose predicate referenced a
literal rather than its column has already been a defect here once. Because of
that, validate the constraint at three levels; the first two have each been
individually insufficient in this repo's history:

```
DDL inspection      predicate references the actual status column
Database behaviour  two ACTIVE versions cannot coexist, under concurrency
Catalogue check     the intended index exists and is usable
```

A `CREATE INDEX` that ran is not evidence the index is the one meant, and an
index that exists is not evidence the database will refuse the second row.

### Status set, and why superseded is retained

```
PENDING      created, not yet usable
ACTIVE       the one version an execution may resolve
SUPERSEDED   replaced by a newer version; retained for rollback and audit
REVOKED      withdrawn; terminal and one-way
FAILED       activation did not complete
```

At most one `ACTIVE` per (connector, key), per tenant.

`FAILED` is distinct from `SUPERSEDED` on purpose. A version whose activation
did not complete was never usable, and collapsing it into "superseded" would
claim it once served traffic — which is exactly the question an incident
review asks. A credential version is **immutable after creation except for its
lifecycle state**.

`SUPERSEDED` is kept rather than deleted because rollback-safe rotation means
returning to the previous version, and a deleted row cannot be returned to.
`REVOKED` is terminal and one-way, mirroring connector revocation for the same
reason: restoring a revoked credential would return a compromised secret to
service without rotating it.

**Stored lowercase, and enforced in code rather than in prose.** A documented
convention is not a control. Declare one canonical enum and derive everything
from it:

```python
class CredentialStatus(str, Enum):
    PENDING = "pending"
    ACTIVE = "active"
    SUPERSEDED = "superseded"
    REVOKED = "revoked"
    FAILED = "failed"
```

Then build the partial index predicate from `CredentialStatus.ACTIVE.value`
wherever the migration framework permits it, rather than retyping `'active'`
— and keep a database-level regression test proving two `ACTIVE` versions
cannot coexist, because deriving the predicate correctly is not evidence the
database refuses the second row.

This matters because the predicate is a string comparison against the column,
so a case mismatch yields an index that silently matches nothing: I7a's defect
wearing a different hat. Note also that M1.4 collapsed three drifting state
enums into one for exactly this reason — do not let credentials reintroduce
the pattern with a second, uppercase copy.

### Version pinned at execution time, recorded on the invocation

The invariant says *at execution time*, and that is what to implement:
resolution reads the active version when the adapter runs, and the version
actually used is written to the invocation record.

**This is a deliberate divergence from the connector-authority snapshot**,
which ADR 0002 pins at *acceptance*. The rule:

```
Connector authority   captured at acceptance, for standard in-flight semantics
Credential authority  revalidated at EVERY point a secret is resolved or used
```

The asymmetry is defensible rather than arbitrary. Connector revocation
governs whether accepted work may *continue*; credential withdrawal governs
whether the platform may still *present that secret to an external system*.
Those are different questions and deserve different answers.

Under asynchronous dispatch:

```
accepted under connector v4 → connector later standard-revoked
                            → queued work cancelled under REV-001

accepted under credential v7 → credential v7 revoked before execution
                             → execution must not resolve or use v7
```

Today `accepted_at ≈ execution_started_at` and the two rules coincide, so the
synchronous implementation cannot distinguish them. **That is the trap.**
Implement the revalidation-at-resolution rule explicitly even though nothing
can currently violate it, or async dispatch will inherit acceptance-time
credential authority by default — a decision made accidentally, which is the
one thing REV-001 and REV-002 exist to prevent.

### The authority snapshot carries identifiers, never entitlement

```
connector_id
connector_version
credential_version_id
tenant_id
accepted_at
authority_decision_id
```

Identifiers and policy context only. The snapshot must never contain the raw
secret, and must never constitute an unconditional entitlement to retrieve it
later. At execution the runtime resolves the credential version **again** and
verifies it is still usable. A snapshot that carried the secret would make
I13a unenforceable by construction: revocation could not reach work that had
already been handed the value.

### No raw secret persistence is a schema property, not a habit

`connector_credentials` stores a reference and metadata. There is no column a
raw value could go in. Enforce it three ways, because each catches a different
mistake:

1. no value column exists — a developer cannot store one without a migration
2. the create/rotate endpoints reject any payload field that is not a valid
   `secret://` reference, with the same forbidden-key check `ConnectorCreate`
   already applies
3. a test that asserts the emitted outbox event, the API response, and the log
   line for a rotation contain neither the reference's resolved value nor any
   high-entropy literal

### Events

```
credential.version.created
credential.version.activated
credential.version.superseded
credential.version.revoked
credential.rotation.completed
credential.rotation.failed
credential.resolution.denied
```

Payloads carry the reference, the version, the actor and the reason — never a
value. The existing outbox envelope (`event_id`, `aggregate_version`,
`schema_version`) applies unchanged.

`credential.resolution.denied` is the one that earns its place: it is the
observable half of I13a. Without it, "was a withdrawn credential ever asked
for?" is unanswerable, and a denied resolution is exactly the signal that
distinguishes a misconfiguration from an attack.

**Subject-tree consequence, verified against the running configuration.** The
publisher prefixes every subject with `favl.` and the stream captures
`favl.>`, so these are delivered without change. But they form a second
top-level tree — `favl.credential.*` alongside `favl.connector.*` — so a
consumer subscribed only to `favl.connector.>` will not receive credential
lifecycle events.

That is a deliberate domain decision: credential lifecycle is its own
aggregate. **State it explicitly in the consumer contract rather than "fixing"
it by renaming the events.** A rename would resolve the symptom by asserting
that credentials are part of the connector aggregate, which is a modelling
claim, and one nobody would have made on purpose.

### Metrics

```
favl_credential_resolution_total{result}
favl_credential_rotation_total{result}
favl_credential_active_versions
favl_credential_revoked_use_attempt_total
favl_credential_secret_boundary_violation_total
```

`favl_credential_secret_boundary_violation_total` should never be non-zero. A
counter that only ever reads zero is still worth having — it is the difference
between "we believe this cannot happen" and "we would know". Per ADR 0001 I10,
it must not be maintained solely by the component it describes.

## Implementation order

```
 1. write the credential-revocation gate FIRST and watch it fail
 2. immutable credential-version persistence, secret references only
 3. one-active-version enforcement
 4. activation and rotation, transactionally
 5. invocation-time credential resolution and authorisation
 6. supersession and rollback rules
 7. revocation and stale-version rejection
 8. disclosure controls across every output boundary
 9. outbox, audit, metrics, mutation coverage
10. re-run the M1.2, M1.3 and M1.4 gates for regression
```

Step 1 before step 2 is not ceremony. A gate written after the implementation
tends to assert what the code does; a gate written first, and watched failing,
asserts what was wanted. M1.4 produced two defects that only a live gate
found, both in code whose unit tests were green.

Step 10 is not optional. M1.4 needed a full `verify_outbox.sh` re-run to prove
it had not weakened M1.2, and credential resolution sits directly in the
invocation path that M1.3 and M1.4 gate.

## Mutation targets

Each must be killed by a named test, per `scripts/mutate.py`:

```
remove credential-status check
remove tenant check
resolve superseded version
resolve revoked version
persist raw secret
include secret in event
include secret in trace
permit two active versions
skip activation transaction
reuse prior credential on retry
```

The last is the one that will not be reachable until a retry path exists — it
belongs to REV-002, and writing it early as a skipped test with a reason is
better than remembering it later.

## Gates — M1.5 is not done until each is observed

| # | Gate | Must be failure-validated by |
|---|---|---|
| 1 | An invocation uses only the active version | pinning a superseded version and watching the invocation be refused |
| 2 | Rotation is atomic | concurrent rotations; the partial index must refuse the second |
| 3 | Rollback restores the prior version | rotating twice, rolling back, asserting the invocation uses v1 |
| 4 | A revoked credential cannot be reactivated | attempting it and getting 409 |
| 5 | No raw secret reaches state, events, logs or API | planting a literal and asserting every surface refuses or redacts it |
| 6 | Credential revocation stops new use immediately | the I12 pattern: revoke mid-flight, next invocation refused |
| 7 | Manifest validation refuses a tampered package | altering a checksum |

Gate 6 is the one to write first. It is the same shape as M1.4's gate, which
is already proven, and it will expose the credential/connector authority
interaction early rather than at the end.

## Standing obligations that M1.5 must not trip

`make check` runs `scripts/check_dormant_obligations.py`. If M1.5 introduces
a retry path, a worker, or a credential-invalidation routine, REV-001/002/003
activate and the build fails until the named control exists. That is intended.
**Do not delete a trigger to make the build pass** — amend ADR 0002 with the
date and the reason, or add the control.

REV-002 is the likely one: credential rotation plus retry is exactly the
combination where an attempt inherits authority it should have had to re-earn.

## Explicitly out of scope

Emergency revocation. It stays designed-and-unbuilt (ADR 0002) until there is
a concrete operational requirement. Unreachable security code cannot be
failure-validated and therefore creates false confidence — the preconditions
for building it are listed in ADR 0002 and none are met.
